## 一、核心理念

### 1.1 质量门原则

**每个阶段完成后，必须通过该阶段的质量门才能进入下一阶段。**

设计 → 【设计质量门】 → 开发 → 【开发质量门】 → 测试 → 【测试质量门】 → 上线/验收
         ↓ 未通过退回设计      ↓ 未通过退回开发      ↓ 未通过退回测试

> 下游阶段不负责发现上游阶段的问题。测试阶段发现设计问题，说明设计质量门失效；测试阶段发现大量开发问题，说明开发质量门失效。

### 1.2 质量门职责分工

| 质量门     | 负责人      | 职责                                     |
| ---------- | ----------- | ---------------------------------------- |
| 设计质量门 | 产品/架构师 | 确保设计方案完整、合理、可开发           |
| 开发质量门 | 开发工程师  | 确保代码实现符合设计、可运行、无阻塞问题 |
| 测试质量门 | 测试工程师  | 确保功能完整、无阻塞问题、达到上线标准   |


## 二、测试类型定义

| 测试类型             | 说明                                            | 执行人                 | 执行时机               |
| -------------------- | ----------------------------------------------- | ---------------------- | ---------------------- |
| **单元测试**         | 单个API接口、函数、组件的功能验证               | 开发者                 | 开发过程中             |
| **集成测试**         | 前后端联调、数据库交互验证                      | 开发者                 | 模块开发完成后         |
| **功能测试**         | 按需求文档逐功能验证                            | 测试者/产品            | 每批次交付前           |
| **回归测试**         | 已有功能不受新代码影响                          | 测试者                 | 每次代码变更后         |
| **部署后端到端测试** | 真实/无头浏览器走完整用户路径，验证部署真的可用 | 部署执行者（含Claude） | **每次部署后（强制）** |
| **验收测试**         | 项目经理对交付成果进行验收                      | 项目经理/用户          | 批次交付时             |

### 2.1 测试执行时机

| 阶段       | 测试类型             | 说明                                           |
| ---------- | -------------------- | ---------------------------------------------- |
| 开发中     | 单元测试 + 集成测试  | 开发者自测                                     |
| 代码提交前 | 集成测试             | 确认不影响已有功能                             |
| 批次交付前 | 功能测试 + 回归测试  | 按验收标准清单逐项验证                         |
| **部署后** | **部署后端到端测试** | **浏览器走完整路径，通过后才可宣布"部署完成"** |
| 批次交付时 | 验收测试             | 项目经理签字确认                               |

### 4.3 真实场景端到端验证（强制，DoD 核心）

> 🔑 **总原则（Definition of Done）**：任何工作——无论是**开发环境改完一个功能**，还是**部署到生产**——都必须用**真实使用场景**在浏览器里走通，才能称为"完成"。改完代码不等于完成，要在浏览器里像真实用户那样操作走通、确认无误，才算完成。

> ⚠️ **来自真实教训**：曾多次出现"curl 测接口返回 200、宣布完成，但用户浏览器登录失败/白屏"。根因：**curl 绕过了浏览器行为**（CORS、JS 执行、登录后的连锁请求），curl 通过 ≠ 用户可用。

**适用节点（两个都强制）**

| 节点                      | 环境                       | 端到端验证要求                                               |
| ------------------------- | -------------------------- | ------------------------------------------------------------ |
| **开发完成一个功能/修改** | 开发环境（localhost:3000） | 浏览器打开对应页面，实际操作该功能走通，F12 无报错，才能标记该功能"开发完成" |
| **部署/更新到生产**       | 生产环境（124.222.151.69） | 浏览器走完整用户路径（登录→首页→核心页面），才能宣布"部署完成" |

**改了接口，不能只测接口本身，必须测调用它的前端页面在浏览器里是否正常。**

#### 4.3.1 验证方法分级（必须区分并如实报告）

| 级别        | 方法                      | 能发现                        | 结论表述                                      |
| ----------- | ------------------------- | ----------------------------- | --------------------------------------------- |
| L1 服务存活 | `systemctl` / `docker ps` | 进程在跑                      | 只能说"服务已启动"                            |
| L2 接口连通 | `curl` 打单接口           | 接口可达                      | 只能说"接口可达"，**发现不了 CORS**           |
| L3 端到端 ✅ | **浏览器走完整路径**      | CORS、白屏、连锁500、前端报错 | 通过后才可说"完成、可使用"（开发/部署同标准） |

#### 4.3.2 端到端必测清单

**A. 开发完成时（开发环境 localhost:3000）**

[ ] 浏览器打开开发前端，本次改动的页面正常渲染（非白屏）
[ ] F12 控制台无红色报错
[ ] 实际操作本次开发/修改的功能，完整走通（增删改查、跳转、下钻等）
[ ] 涉及的接口在页面上真实触发并返回正确结果（不是单独 curl）
[ ] 登录态、权限相关改动，换对应角色账号验证

**B. 部署完成时（生产环境 124.222.151.69）**

[ ] 浏览器打开生产地址，首页正常渲染（非白屏）
[ ] F12 控制台无红色报错（重点：CORS / Network Error）
[ ] 实际登录成功进入系统
[ ] 登录后 Dashboard 及连锁接口无 500
[ ] 核心页面逐个点开无报错
[ ] 非管理员账号权限正常

#### 4.3.3 推荐工具

用 `playwright-ui-auto` skill 做无头浏览器自动化验证——真实浏览器环境，自动捕获 CORS、白屏、连锁 500，比人工点更可靠、可复现。

#### 4.3.4 报告纪律（开发汇报"完成"、部署汇报"完成"均适用）

- 必须区分"L2 接口验证"与"L3 端到端验证"，不得用"测试通过""完成了"笼统概括
- 有未验证项必须明说，禁止在只做了 L1/L2 的情况下宣布"完成 / 可以正常使用"
- "代码写完"只能说"代码写完，待端到端验证"，不得直接说"功能完成"

### 5.5 问题分级标准

| 级别           | 定义                                 | 示例                                                         | 处理方式                     |
| -------------- | ------------------------------------ | ------------------------------------------------------------ | ---------------------------- |
| **P0（阻塞）** | 核心功能不可用、页面打不开、数据丢失 | 登录失败、核心接口（如登录/dashboard/overview）返回404、提交数据丢失 | 立即修复，修复前停止测试     |

| **P3（建议）** | 体验优化、非功能需求                 | 加载速度可优化、交互可更流畅                                 | 记录为优化建议，后续版本考虑 |

## 六、上下文压缩测试场景

**目标**：验证 AI 在长对话中不会因上下文压缩而丢失关键信息（呼应 CLAUDE.md 铁律"怀疑失忆时主动重读 state.json"）。

| 检查项       | 标准                                                    | 状态 |
| ------------ | ------------------------------------------------------- | ---- |
| 对话恢复     | 对话超过一定长度后，AI 能主动读取 state.json 恢复上下文 | ☐    |
| 关键信息保留 | 字段定义、枚举值、API设计等核心信息不丢失               | ☐    |
| 状态一致性   | 当前任务状态（进行中/已完成）与 state.json 记录一致     | ☐    |

**触发条件**：当对话长度超过 50 条消息，或用户提示"你刚才不是已经确认过了吗"时，检查该项。
